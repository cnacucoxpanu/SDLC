# Хеширование паролей PBKDF2-HMAC-SHA256 со случайной солью

## Контекст и постановка задачи

Пароли не должны храниться в открытом виде, одинаковые пароли должны давать разные хеши (REQ-SEC-001). Файлы базы — обычные текстовые файлы, которые может открыть любой пользователь компьютера. Как хранить пароли?

## Драйверы решения

* Требование REQ-SEC-001.
* Только стандартная библиотека JDK (ADR-0001).
* Стойкость к перебору при утечке файла `users.tsv`.

## Рассмотренные варианты

* PBKDF2-HMAC-SHA256, соль 16 байт, 20 000 итераций (`javax.crypto`)
* SHA-256 от пароля с солью
* bcrypt / Argon2 из сторонней библиотеки

## Итог решения

Выбранный вариант: «PBKDF2-HMAC-SHA256», потому что это стандартный медленный алгоритм, доступный в JDK без зависимостей. Формат хранения: `соль_hex:хеш_hex`; сравнение — `MessageDigest.isEqual` (за постоянное время).

### Последствия

* Хорошо, потому что перебор паролей замедлен в тысячи раз по сравнению с SHA-256.
* Плохо, потому что вход занимает 20–50 мс (незаметно для пользователя).

### Подтверждение

Автоматическая проверка: хеш не содержит пароль, два хеша одного пароля различаются, `matches` принимает верный и отклоняет неверный пароль.

## Плюсы и минусы вариантов

### PBKDF2

* Хорошо, потому что входит в JDK и рекомендован NIST SP 800-132.

### SHA-256 с солью

* Плохо, потому что быстрый хеш легко перебирается на GPU.

### bcrypt / Argon2

* Хорошо, потому что ещё стойче.
* Плохо, потому что нужна внешняя библиотека.

## Дополнительная информация

В раунде 1 заказчик спросил, почему вход стоит 16 ч; после объяснения оценка снижена до 12 ч за счёт отказа от экрана смены пароля (пароли выдаёт лаборант). Связано: REQ-FUNC-001, REQ-SEC-001.
