# Текстовое описание UML-моделей и связь диаграмм между собой

## Контекст и постановка задачи

Для проекта нужна модель динамического поведения: варианты использования, активность, состояния и последовательности. Диаграммы должны храниться в репозитории, меняться вместе с требованиями и не противоречить друг другу, SRS и коду. Как строить диаграммы и как связать их между собой?

## Драйверы решения

* Изменения диаграмм должны быть видны в истории Git (SRS 3.5.10).
* Каждый элемент поведения должен прослеживаться до требования SRS и класса из SDD.
* Рекомендация задания: использовать текстовое описание UML.
* В проекте нет платных компонентов (SRS 3.5.7).

## Рассмотренные варианты

* Текстовые файлы PlantUML (`docs/uml/*.uml`) и картинки PNG рядом с ними
* Графический редактор (draw.io) с файлами диаграмм
* Только картинки в документах

## Итог решения

Выбранный вариант: «Текстовые файлы PlantUML и PNG», потому что только текст даёт построчное сравнение версий и ревью, а PNG позволяет показать диаграмму в SDD и отчёте.

### Механизм построения

1. Из SRS выделяются актёры и прецеденты (`use-cases.md`). Каждому прецеденту соответствует требование `REQ-*`.
2. Основной и альтернативные потоки прецедентов сводятся в диаграммы активности. Шаг потока становится действием, альтернативный поток становится ветвью решения.
3. Объекты, которые меняются в потоках (бронь и оборудование), получают диаграммы состояний. Действие, меняющее объект, становится событием перехода, условие ветвления становится сторожевым условием.
4. Шаги системы раскрываются диаграммами последовательности. Линии жизни берутся из классов V-002, сообщения — из методов V-005.

### Связи диаграмм

| Откуда | Куда | Что связывает |
|--------|------|---------------|
| Требование `REQ-*` | Прецедент `UC-NN` | поле «Требования» в `use-cases.md` |
| Прецедент | Диаграмма активности | шаги потоков становятся действиями |
| Действие активности | Переход состояния | действие «Отметить выдачу» и переход `issue` |
| Переход состояния | Сообщение последовательности | переход `issue` и вызов `IssueService.issue()` |
| Сообщение | Метод класса | контракты V-005 |
| Связь `include` | Фрагмент `ref` | UC-09 подключается в `sd Бронирование оборудования` |

### Последствия

* Хорошо, потому что изменение требования можно проследить до диаграмм и классов.
* Хорошо, потому что диаграммы проверяются вместе с кодом на ревью.
* Плохо, потому что файлы `.uml` и PNG нужно обновлять вместе.
* Плохо, потому что на момент решения в рабочей среде не было Java: PNG нарисованы вручную по файлам `.uml`, а сами файлы не проверены запуском PlantUML.

### Подтверждение

При появлении JDK файлы обрабатываются командой `java -jar plantuml.jar docs/uml/*.uml`. Перед завершением итерации проверяется, что каждый прецедент связан с требованием и что имена сообщений совпадают с методами V-005.

## Плюсы и минусы вариантов

### Текстовые файлы PlantUML

* Хорошо, потому что видны построчные изменения.
* Хорошо, потому что инструмент бесплатный.
* Плохо, потому что для рендера нужна Java.

### Графический редактор

* Хорошо, потому что удобно расставлять элементы вручную.
* Плохо, потому что изменения в файле трудно сравнивать.

### Только картинки

* Плохо, потому что диаграмму нельзя поправить без исходника.
