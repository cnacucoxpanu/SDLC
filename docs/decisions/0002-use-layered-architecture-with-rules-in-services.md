# Слоистая архитектура: бизнес-правила только в сервисах

## Контекст и постановка задачи

Правила бронирования, статусов и прав доступа (REQ-FUNC-005, REQ-FUNC-006, REQ-SEC-001) должны проверяться автоматически и одинаково, откуда бы ни пришло действие. Где размещать бизнес-правила и как разбить код, чтобы над ним могли работать два разработчика?

## Драйверы решения

* Автоматическая проверка правил без запуска интерфейса (раздел 4 SRS).
* Безопасность: студент не должен обойти проверку прав через интерфейс (REQ-SEC-001).
* Параллельная работа middle и junior без конфликтов в одних файлах.
* Возможность заменить хранилище (SRS 3.5.6).

## Рассмотренные варианты

* Слои `ui / service / storage / model`, правила в сервисах
* Правила в обработчиках кнопок Swing
* MVC с правилами в контроллерах

## Итог решения

Выбранный вариант: «Слои, правила в сервисах», потому что только он позволяет тестировать правила без UI и разделить работу: junior делает диалоги и экспорт (`ui`), middle — правила (`service`).

### Последствия

* Хорошо, потому что `SelfTest` проверяет все требования вызовами сервисов.
* Хорошо, потому что изменение правила затрагивает один класс.
* Плохо, потому что больше классов и передача `actor` в каждый метод.

### Подтверждение

Код-ревью: в пакете `labequip.ui` нет импортов `labequip.storage`; сервисы не импортируют `javax.swing`. Проверяется поиском по импортам перед завершением каждой итерации.

## Плюсы и минусы вариантов

### Слои, правила в сервисах

* Хорошо, потому что тестируемость и изоляция.
* Нейтрально, потому что требует дисциплины при ревью.

### Правила в обработчиках Swing

* Хорошо, потому что быстрее написать первую версию.
* Плохо, потому что правила дублируются и не тестируются автоматически.

### MVC с контроллерами

* Хорошо, потому что знакомый паттерн.
* Плохо, потому что контроллеры Swing всё равно привязаны к UI; выигрыша перед сервисами нет.
